# HU-010: Gestión de sedes y clínicas afiliadas

## Distribución

- `Administracion/back/src/sede/` y `clinica/`: modelos MongoDB, validación y servicios de alta, edición, consulta y desactivación lógica. Django es dueño de la escritura.
- `Administracion/front-web/src/CatalogoApp.tsx`: formularios y listados administrativos en React.
- `Usuario/back/src/main/java/com/pikafit/usuario/clinica/`: consulta de clínicas activas en Spring Boot, sin escritura.
- `Usuario/front-movil/`: pantalla Kotlin de clínicas activas con dirección y teléfono.

## Contratos

Administración expone `/api/v1/sedes/` y `/api/v1/clinicas/` para listar y registrar; el detalle admite `PATCH` y `DELETE` (desactivación). Requiere una sesión de administrador del gimnasio. Usuario expone `GET /api/v1/clinicas` y solo devuelve clínicas activas. El RUC exige 11 dígitos, prefijo permitido y dígito verificador; también se rechaza el duplicado.

Las sedes y clínicas inactivas permanecen almacenadas para conservar el historial. Los servicios incluyen consultas de entidad activa para futuras asignaciones y operaciones.

## Verificación realizada

- Compilación de React, Spring Boot y Kotlin Android.
- Ocho pruebas de Django para datos obligatorios, RUC, duplicados y desactivación.
- Prueba de Spring Boot para el filtro de clínicas activas.
- Migraciones Django y prueba CRUD en una base MongoDB temporal, con conservación de registros tras desactivar.

## Integración pendiente

HU-001 sigue fuera de `develop`. El formulario React muestra datos de demostración mientras no se integre la sesión administrativa real; el token de ejemplo se lee de `sessionStorage` bajo `pikafit_admin_access`. El bloqueo de acceso del personal de clínicas y de validación de pases debe conectarse a los módulos de autenticación y pases cuando estén disponibles. No se debe marcar esta HU como terminada ni juntar su PR hasta verificar esos criterios y la dependencia HU-001.
